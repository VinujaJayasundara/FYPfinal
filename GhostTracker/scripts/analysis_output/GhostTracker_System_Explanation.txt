1. PROBLEM STATEMENT & MOTIVATION
================================================================================

Existing fitness platforms like Strava, Nike Run Club, and Garmin Connect
suffer from three fundamental limitations:

  (a) PRIVACY: All running data (GPS tracks, health metrics, location history)
      is uploaded to centralized cloud servers. Users have no data sovereignty.
      A single breach exposes millions of users' movement patterns.

  (b) CONNECTIVITY: These apps require internet to sync results, compare with
      friends, and update leaderboards. In rural Sri Lanka, parks without
      cellular coverage, or underground running tracks, the apps are useless.

  (c) FAIRNESS: Leaderboards rank by absolute pace (e.g., 4:00/km vs 7:00/km).
      An elite runner who jogs casually will always rank above a beginner who
      gives 100% effort. This discourages beginners and makes competition
      inherently unfair across age groups, genders, and fitness levels.

Ghost-Tracker solves all three problems through three core innovations:

  - RII (Relative Improvement Index): You race against your own past best,
    not against others' absolute speed.
  - NPI (Normalized Performance Index): A z-score model that normalizes pace
    expectations by age, BMI, gender, altitude, and distance.
  - CRDT-based P2P Sync: Leaderboards synchronize via Bluetooth without any
    central server, using mathematically proven convergence guarantees.

3. PHASE 1 - CORE ALGORITHM ENGINE (COMPLETED)
================================================================================

3.1  SPATIAL MODULE (src/core/spatial/)
-----------------------------------------

  (a) Haversine Distance Calculator (haversine.ts)
      - Calculates great-circle distance between two GPS coordinates
      - Uses the standard Haversine formula on Earth's surface
      - Provides both meter and kilometer variants
      - Used for: cumulative distance tracking during a run

  (b) GPS Filter (gpsFilter.ts)
      - Rejects invalid GPS readings caused by satellite noise
      - Validation rules:
        * Velocity cannot exceed 25 km/h (a run, not a vehicle)
        * GPS accuracy must be better than 50 meters
        * Teleportation rejection: >50m jump in 1 second is impossible
        * Coordinates must be within valid latitude/longitude bounds
      - Returns filtered points + a rejection log with specific reasons:
        NULL_COORDINATES, VELOCITY_EXCEEDED, LOW_ACCURACY,
        IMPLIED_SPEED_EXCEEDED, TIMESTAMP_NOT_MONOTONIC

  (c) Pace Calculator (paceCalculator.ts)
      - Instant pace: pace between two consecutive GPS points
      - Rolling pace: smoothed average over a sliding window
      - Average pace: overall session pace
      - Unit conversions: pace <-> speed, formatting (e.g., "5:30 /km")

3.2  FAIRNESS MODULE (src/core/fairness/)
-------------------------------------------

  (a) RII Engine (riiEngine.ts)
      The Relative Improvement Index is the primary fairness metric:

        RII = PB_pace / Current_pace

      - RII > 1.0  =  Running FASTER than your personal best (Ghost)
      - RII = 1.0  =  Matching your Ghost exactly
      - RII < 1.0  =  Running SLOWER than your Ghost

      This is mathematically fair because:
        * A 5% improvement ALWAYS produces RII = 1.0526
        * This holds for ALL ability levels (beginner 7:00/km or elite 3:30/km)
        * Same effort = same score, regardless of absolute speed

      Status Scale:
        RII >= 1.10  ->  "Crushing It!"  (exceptional performance)
        RII >= 1.00  ->  "On Pace"       (matching or beating Ghost)
        RII >= 0.95  ->  "Slightly Behind" (close to Ghost)
        RII <  0.95  ->  "Behind Ghost"  (needs to push harder)

  (b) Ghost Comparator (ghostComparator.ts)
      - Binary search to find Ghost's position at current elapsed time
      - Calculates lead/lag distance in real-time (positive = ahead)
      - Generates complete PaceData objects for the UI every second

3.3  CRDT MODULE (src/core/crdt/) - P2P Consensus
----------------------------------------------------

  CRDTs (Conflict-free Replicated Data Types) allow multiple devices to
  independently update leaderboards and merge without conflicts.

  (a) G-Counter (gCounter.ts)
      A Grow-Only Counter implementing Strong Eventual Consistency:
      - State: {replicaId -> count} map (each device has its own counter)
      - Merge: element-wise MAX across all replica IDs
      - Guarantees: Commutative, Associative, Idempotent
      - This means: merge(A,B) = merge(B,A), no matter the order of merges

  (b) Merge Engine (mergeEngine.ts)
      - Orchestrates merging G-Counter states + leaderboard entries
      - Conflict resolution: highest RII wins; ties broken by most recent
        timestamp (Last-Writer-Wins per device+route pair)

  (c) State Vector (stateVector.ts)
      - JSON serialization with BLE MTU validation (max 512 bytes)
      - Creates sync payloads for Bluetooth transmission

3.4  DATA LAYER (src/data/)
-----------------------------
  - 8 TypeScript domain interfaces (TelemetryPoint, RunSession, GhostRecord,
    LeaderboardEntry, CRDTState, SyncPayload, PaceData, DeviceProfile)
  - 6-table SQLite schema with WAL mode for concurrent read/write
  - Repository pattern: sessionRepo, ghostRepo, telemetryRepo, leaderboardRepo

3.5  TEST SUITE (6 Test Files)
--------------------------------
  - riiEngine.test.ts       -> RII calculation, cumulative RII, edge cases
  - haversine.test.ts       -> Known distance benchmarks (Colombo-Kandy, etc.)
  - gpsFilter.test.ts       -> Coordinate validation, velocity, accuracy
  - paceCalculator.test.ts  -> Instant/rolling/average pace, conversions
  - gCounter.test.ts        -> CRDT merge properties (COM, ASSOC, IDEMP)
  - crdtMerge.test.ts       -> Full merge pipeline, convergence verification

This is the statistical modeling phase where we built and validated the

4A. WHAT DATA WE NEEDED
------------------------

The NPI model needs to predict a runner's EXPECTED PACE given their profile
and environmental conditions. To build this model, we needed data with:

  INPUT FEATURES (what we feed into the model):
    1. Age (years)            - Older runners are naturally slower
    2. BMI (kg/m^2)           - Higher BMI increases pace due to weight
    3. Altitude (meters)      - Higher altitude = thinner air = slower pace
    4. Route Distance (meters)- Longer routes cause fatigue = slower pace
    5. Gender (Male/Female)   - Physiological differences affect pace

  TARGET VARIABLE (what we predict):
    - Average Pace (seconds per kilometer)

  The idea is: if we know a runner's age, BMI, gender, the altitude they're
  running at, and the route distance, we can predict what pace they SHOULD
  achieve. Then we compare their ACTUAL pace to this expectation to get
  a fair score (the NPI z-score).


4B. HOW WE GENERATED THE TRAINING DATA
-----------------------------------------

Script: generate_npi_training_data.py

Since collecting real-world data from 200 runners across multiple locations
is impractical for an FYP, we generated SYNTHETIC training data using a
known ground-truth model. This is a scientifically valid approach because:
  - We know the TRUE relationship between features and pace
  - We can verify the regression RECOVERS these true coefficients
  - If it does, the model is proven to work correctly

DATA GENERATION PROCESS:

  Step 1: Define Ground-Truth Coefficients
  -----------------------------------------
  We defined the "true" relationship between features and pace:

    pace = 205.0                      (base pace for ideal conditions)
         + 1.85  * age                (+1.85 s/km per year of age)
         + 3.50  * BMI                (+3.50 s/km per BMI unit)
         + 0.038 * altitude_m         (+0.038 s/km per meter of altitude)
         + 0.005 * route_distance_m   (+0.005 s/km per meter of distance)
         + 15.0  * gender_female      (+15 s/km for female runners)
         + noise                      (random Gaussian noise, sigma=12 s/km)

  These coefficients are based on sports science research:
    - Age decline: ~1.5-2% per year after peak (25-30 years old)
    - BMI effect: each kg/m^2 above optimal adds ~3-4 s/km
    - Altitude: ~3-4% slower per 1000m of elevation gain
    - Fatigue: longer distances naturally reduce average pace
    - Gender gap: ~12-18 s/km difference on average

  Step 2: Generate 200 Runner Profiles
  --------------------------------------
  We created 200 diverse runner profiles:
    - 100 Male runners with Sri Lankan names
    - 100 Female runners with Sri Lankan names
    - Ages: uniformly distributed 18-62 years
    - Heights: normally distributed (Male: 172+/-8cm, Female: 162+/-7cm)
    - Weights: normally distributed (Male: 75+/-12kg, Female: 60+/-10kg)
    - BMI: calculated from height and weight
    - Locations: 10 real Sri Lankan locations with actual altitudes:
        * Bellanwila Park (15m)
        * KDU Clubhouse (45m)
        * Viharamahadevi Park (8m)
        * Diyatha Uyana (12m)
        * Kandy Lake (510m)
        * Nuwara Eliya Track (1868m)
        * Horton Plains (2160m)
        * Ella Mountain Trail (1041m)
        * Galle Face Green (3m)
        * Sigiriya Base (370m)
    - Route distances: 1km to 10km (10 different options)
    - Each runner has a unique improvement rate (0.5% to 4% per session)

  Step 3: Generate 6 Sessions Per Runner
  ----------------------------------------
  For each of the 200 runners, we generated 6 training sessions:
    - Session 1: baseline pace (ground-truth + noise)
    - Sessions 2-6: progressively improving by the runner's improvement rate
    - Each session adds Gaussian noise (sigma=12 s/km) for realism
    - Pace clamped to realistic range: 2:30/km to 12:00/km

  TOTAL DATASET: 200 runners * 6 sessions = 1,200 data points

  Output Files:
    - npi_training_data.csv (1,200 rows, 17 columns)
    - npi_runner_profiles.json (200 profiles with ground-truth coefficients)
    - npi_data_summary.txt (statistical summary)


4C. HOW WE TRAINED THE MODEL
-------------------------------

Script: fit_npi_model.py

MODEL TYPE: Multiple Linear Regression (using Normal Equation)

We chose Multiple Linear Regression because:
  1. The relationship between features and pace is approximately linear
  2. It's interpretable (each coefficient has a clear physical meaning)
  3. No external library dependencies (we implemented it from scratch)
  4. Works well for this type of physiological data

TRAINING PROCESS:

  Step 1: Feature Matrix Construction
  ------------------------------------
  We construct the design matrix X with 6 columns:
    Column 0: 1             (intercept term)
    Column 1: age           (years)
    Column 2: BMI           (kg/m^2)
    Column 3: altitude_m    (meters above sea level)
    Column 4: distance_m    (route distance in meters)
    Column 5: gender_female (1 if female, 0 if male)

  Target vector y: average pace in seconds per kilometer

  Step 2: Train/Test Split (80/20)
  ---------------------------------
  - Random permutation with seed=42 for reproducibility
  - Training set: 960 samples (80%)
  - Test set: 240 samples (20%)
  - The model is trained ONLY on the training set
  - The test set is kept completely separate for unbiased evaluation

  Step 3: Normal Equation Solution
  ----------------------------------
  We solve for the optimal coefficients using the closed-form solution:

    beta = (X^T * X)^(-1) * X^T * y

  Where:
    X^T = transpose of feature matrix
    (X^T * X)^(-1) = inverse of the Gram matrix
    y = target vector (actual paces)

  This gives us the exact least-squares solution without iterative
  optimization (no gradient descent needed).

  Step 4: Model Outputs
  -----------------------
  The fitted model produces:
    - Coefficient vector (beta): 6 values (intercept + 5 features)
    - Predictions: y_pred = X * beta
    - Residuals: y - y_pred (actual - predicted)
    - Residual standard deviation (sigma): used for NPI z-score calculation

  Step 5: NPI Score Calculation
  ------------------------------
  Once we have the model, the NPI for any runner is:

    NPI = (Expected_pace - Actual_pace) / sigma

  Where:
    Expected_pace = intercept + age*beta_age + BMI*beta_bmi + ...
    Actual_pace   = the runner's real recorded pace
    sigma         = residual standard deviation (24.16 s/km)

  NPI Interpretation:
    NPI > +2.0  ->  Exceptional (top ~2.5%)
    NPI > +1.0  ->  Above Average (top ~16%)
    NPI =  0.0  ->  Exactly as expected for their profile
    NPI < -1.0  ->  Below Average (bottom ~16%)
    NPI < -2.0  ->  Needs Work (bottom ~2.5%)

  This is a STANDARD Z-SCORE, so it follows the normal distribution.
